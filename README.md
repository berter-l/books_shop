# API книжного магазина

Backend для книжного магазина на Python и FastAPI. Приложение позволяет регистрировать покупателей и авторов,
просматривать книги, добавлять их в корзину и оформлять заказы. При покупке проверяются баланс пользователя и наличие
нужного количества книг на складе.

Для хранения данных используется PostgreSQL, Redis отвечает за кэширование токенов и временное хранение кодов
подтверждения, а фоновые задачи выполняются через Celery с RabbitMQ.

## Возможности проекта

В приложении реализованы следующие функции:

- Регистрация покупателей и авторов.
- Авторизация по электронной почте и паролю.
- Хеширование паролей с помощью bcrypt.
- Выдача и проверка JWT access- и refresh-токенов.
- Подтверждение электронной почты с помощью кода.
- Просмотр списка книг с пагинацией.
- Получение информации об авторах и их книгах.
- Добавление новых книг авторами.
- Создание корзины и добавление в неё книг.
- Расчёт общей стоимости товаров в корзине.
- Оформление заказов с проверкой баланса и остатков на складе.
- Просмотр заказов пользователя.
- Административное управление заказами и отметка о доставке.
- Отправка электронных писем через фоновые задачи.
- Периодическая очистка таблиц с отозванными токенами.

## Работа с базой данных без ORM

Одна из основных особенностей проекта — работа с PostgreSQL без использования ORM.

Для доступа к базе данных используется Psycopg 3. SQL-запросы написаны вручную и выполняются непосредственно через
`connection.execute()`. В проекте нет SQLAlchemy, SQLModel, Tortoise ORM и других ORM-библиотек.

Такой подход позволяет контролировать SQL-запросы, условия выборки, обновление данных и поведение транзакций
непосредственно в коде приложения.

### Как организована работа с PostgreSQL

**1. SQL-запросы пишутся вручную**

Для чтения, добавления, изменения и удаления данных используются обычные SQL-команды: `SELECT`, `INSERT`, `UPDATE`
и `DELETE`.

Например, при получении данных о пользователе приложение выполняет запрос к таблице `users`, а при добавлении новой книги — запрос `INSERT INTO books`.

**2. Создание таблиц выполняется через SQL**

В файле `main_app/database.py` находятся SQL-команды создания таблиц. При запуске приложения вызывается функция
`create_all_tables()`, которая создаёт необходимые таблицы, если они ещё не существуют.

Отдельная система ORM-моделей и автоматического построения таблиц по классам не используется. Миграции базы данных в проекте также не настроены.

**3. Данные преобразуются вручную**

После выполнения SQL-запроса результаты обрабатываются в коде приложения. Для формирования ответов API используются
Pydantic-схемы, в которые данные передаются вручную.

Pydantic здесь отвечает за проверку и описание данных, а не за работу с базой данных. Pydantic-схемы не являются ORM-моделями.

**4. Параметры передаются отдельно от SQL**

Для передачи значений в запросы используются плейсхолдеры Psycopg, например `%s`. Значения передаются отдельно, а не вставляются непосредственно в строку SQL.

Это помогает корректно обрабатывать входные данные и снижает риск SQL-инъекций при работе с пользовательским вводом.

**5. Используются транзакции PostgreSQL**

При выполнении операций, которые изменяют несколько связанных записей, важно не допустить частичного обновления данных.

В проекте для таких операций предусмотрено явное управление транзакциями с помощью `BEGIN`, `COMMIT` и `ROLLBACK`.
При оформлении заказа также используется `SELECT ... FOR UPDATE`, чтобы блокировать выбранные строки на время транзакции
и снизить риск одновременного списания одних и тех же товаров со склада.

**6. Соединения берутся из пула**

Для работы с PostgreSQL используется `psycopg_pool.ConnectionPool`. Это позволяет переиспользовать соединения и не
создавать новое подключение к базе данных для каждого отдельного запроса.

Содержит функции, связанные с хешированием паролей и работой с JWT.

Содержит логику обработки запросов: регистрацию и авторизацию, работу с книгами и корзинами, оформление заказов и взаимодействие с PostgreSQL.

**`main_app/app/schemes/`**

Содержит Pydantic-схемы для валидации входных данных и формирования ответов API.

**`main_app/app/config/`**

Содержит настройки подключения к сервисам и параметры авторизации.

**`main_app/celery_app.py`**

Содержит конфигурацию Celery для постановки задач отправки электронной почты в очередь.

**`email_app/`**

Содержит Celery-задачи, связанные с отправкой электронных писем.

Содержит периодические задачи, в том числе очистку таблиц отозванных токенов.

## Архитектура приложения

Приложение разделено на несколько частей.

API-маршруты принимают HTTP-запросы и передают обработку в соответствующие сервисы. Сервисный слой содержит логику
приложения и выполняет SQL-запросы к PostgreSQL через Psycopg 3.

Pydantic используется для проверки входных данных и подготовки ответов. Redis хранит временные данные, а Celery
и RabbitMQ позволяют выполнять отдельные операции в фоновом режиме.

PostgreSQL является основным хранилищем: в нём находятся пользователи, авторы, книги, корзины, заказы и сведения об отозванных токенах.

## Установка и запуск

Для запуска проекта предусмотрен Docker Compose.

Перед запуском необходимо проверить настройки подключения к PostgreSQL, Redis и RabbitMQ, а также устранить замечания
по конфигурации, приведённые ниже. В текущей версии исходников есть несколько незавершённых настроек, поэтому запуск
всех сервисов без исправлений не гарантируется.

### 1. Подготовка проекта

Склонируйте репозиторий и перейдите в его корневую директорию:

```bash
git clone <URL_ВАШЕГО_РЕПОЗИТОРИЯ>
cd <ПАПКА_ПРОЕКТА>
```

Вместо указанных значений подставьте адрес своего репозитория и название каталога.

### 2. Настройка конфигурации

Перед запуском проверьте параметры PostgreSQL, Redis, RabbitMQ и JWT.

Также необходимо исправить путь импорта Redis-конфигурации и настроить SMTP, если требуется отправка электронных писем.

Подробности приведены в разделе «Что нужно настроить перед запуском».

### 3. Сборка и запуск

После исправления конфигурации запустите проект из корневой директории:

```bash
docker compose up --build
```

Для запуска контейнеров в фоновом режиме:

```bash
docker compose up --build -d
```

Для просмотра логов:

```bash
docker compose logs -f
```

Для остановки приложения:

```bash
docker compose down
```

Чтобы удалить контейнеры вместе с томами и сохранёнными данными PostgreSQL, Redis и RabbitMQ, используйте:

```bash
docker compose down -v
```

**Внимание:** команда `docker compose down -v` удаляет тома и содержащиеся в них данные. Используйте её только в том случае, если действительно хотите очистить сохранённое состояние сервисов.

## Авторизация

Для доступа к защищённым маршрутам используются JWT-токены.

При регистрации или входе пользователь получает `access_token` и `refresh_token`.

Для пользовательских и авторских маршрутов access-токен передаётся в заголовке:

```http
Authorization-token: <access_token>
```

Для административных маршрутов предусмотрен отдельный заголовок:

```http
Authorization-admin-token: <admin_token>
```

Названия заголовков соответствуют текущей реализации проекта. В коде используется собственный заголовок
`Authorization-token`, а не стандартный формат `Authorization: Bearer ...`.

Время жизни токенов задаётся в `main_app/app/config/jwt_token_conf.py`.
В текущих настройках access-токен действует 10 минут, refresh-токен — 7 дней. Используется алгоритм `HS256`.

Отозванные токены сохраняются в отдельных таблицах PostgreSQL. Для access-токенов также предусмотрено кэширование через Redis.

## API

Ниже перечислены основные маршруты приложения. Полные схемы запросов и ответов доступны в Swagger UI после запуска.

### Пользователи

| Метод | Маршрут | Описание |
|---|---|---|
| POST | `/users` | Регистрация пользователя |
| POST | `/users/verify-email` | Запрос кода подтверждения электронной почты |
| POST | `/users/verify-code?code=123456` | Проверка кода подтверждения |
| POST | `/users/login` | Авторизация по email и паролю |
| POST | `/users/logout` | Отзыв access- и refresh-токенов |
| GET | `/users/me` | Получение профиля текущего пользователя |
| GET | `/users/orders` | Получение заказов текущего пользователя |
| POST | `/users/balance?amount=500` | Пополнение баланса пользователя |

Для регистрации используются поля `first_name`, `last_name`, `email`, `age` и `password`.

Проверка входных данных выполняется через Pydantic-схемы. Например, возраст должен быть положительным целым числом.

### Авторы

| Метод | Маршрут | Описание |
|---|---|---|
| POST | `/authors` | Регистрация автора |
| POST | `/authors/login` | Авторизация автора |
| GET | `/authors` | Получение списка авторов |
| GET | `/authors/{author_id}` | Получение информации об авторе |
| GET | `/authors/{author_id}/books` | Получение информации об авторе и его книгах |

Для создания книги автор использует маршрут `POST /books`.

Обратите внимание: в текущем обработчике маршрута `/authors/{author_id}/books` идентификатор автора берётся из
access-токена, а не из параметра пути. Это поведение стоит учитывать при дальнейшей доработке API.

### Книги

| Метод | Маршрут | Описание |
|---|---|---|
| GET | `/books?page=1&limit=10` | Получение списка книг с пагинацией |
| POST | `/books` | Добавление книги от имени автора |

При добавлении книги передаются следующие данные:

- `title` — название книги;
- `price` — цена;
- `count` — количество экземпляров на складе.

Автор книги определяется по токену, переданному в заголовке `Authorization-token`.

### Корзина и заказы

| Метод | Маршрут | Описание |
|---|---|---|
| GET | `/carts` | Получение активной корзины пользователя |
| POST | `/carts?book_id=1` | Добавление книги в корзину |
| POST | `/orders` | Оформление заказа |

Для работы с корзиной и оформления заказа требуется access-токен пользователя.

При оформлении заказа приложение проверяет активную корзину, наличие необходимой суммы на балансе и количество
экземпляров книг на складе. После успешной проверки создаётся заказ, списываются средства, уменьшается
остаток книг и корзина помечается как использованная.

Основные изменения при оформлении заказа выполняются в транзакции PostgreSQL.

### Административные маршруты

| Метод | Маршрут | Описание |
|---|---|---|
| GET | `/admins/user-orders` | Получение заказов всех пользователей |
| POST | `/admins/orders/{order_id}` | Изменение статуса заказа на доставленный |

Для обращения к этим маршрутам необходим заголовок `Authorization-admin-token`.

При изменении статуса заказа приложение также ставит фоновую задачу отправки письма. Для её успешного
выполнения должны быть настроены Celery-воркер, RabbitMQ и SMTP.

## Примеры запросов

В примерах используется адрес локально запущенного API.

### Регистрация пользователя

```bash
curl -X POST "http://localhost:8000/users" \
  -H "Content-Type: application/json" \
  -d '{
    "first_name": "Иван",
    "last_name": "Иванов",
    "email": "ivan@example.com",
    "age": 28,
    "password": "change-me"
  }'
```

В ответе ожидаются данные с access- и refresh-токенами.

Для дальнейших запросов используйте полученный access-токен.

### Получение списка книг

```bash
curl "http://localhost:8000/books?page=1&limit=10"
```

Параметр `page` указывает номер страницы, а `limit` — количество записей на странице.

### Добавление книги в корзину

```bash
curl -X POST "http://localhost:8000/carts?book_id=1" \
  -H "Authorization-token: <access_token>"
```

Вместо `<access_token>` нужно передать действующий токен пользователя, а `book_id` заменить на существующий идентификатор книги.

### Просмотр профиля

```bash
curl "http://localhost:8000/users/me" \
  -H "Authorization-token: <access_token>"
```

### Оформление заказа

```bash
curl -X POST "http://localhost:8000/orders" \
  -H "Authorization-token: <access_token>"
```

Для успешного оформления заказа у пользователя должна быть активная корзина, достаточный баланс и нужное количество книг на складе.

## Структура базы данных

Таблицы создаются через SQL-команды в `main_app/database.py`. При запуске приложения вызывается функция `create_all_tables()`.

В проекте используются следующие таблицы:

| Таблица | Назначение |
|---|---|
| `users` | Данные покупателей и их баланс |
| `authors` | Данные авторов и информация для авторизации |
| `books` | Книги, цены, количество экземпляров и связь с автором |
| `carts` | Корзины пользователей и статус их использования |
| `cart_items` | Состав корзин |
| `orders` | Заказы, их стоимость, дата, статус и связанные записи |
| `admins` | Данные административной учётной записи |
| `access_token_blacklist` | Отозванные access-токены |
| `refresh_token_blacklist` | Отозванные refresh-токены |

Связи между таблицами, первичные и внешние ключи, ограничения уникальности и проверки значений задаются непосредственно SQL-командами.

Например, структура базы предусматривает проверки, связанные с возрастом пользователя, балансом, количеством книг на складе и допустимыми статусами заказа.


## Фоновые задачи

Для выполнения фоновых задач используется Celery, а в качестве брокера сообщений — RabbitMQ.

В проекте предусмотрены следующие задачи:

- Отправка электронных писем.
- Постановка задач отправки писем в очередь `emails`.
- Периодическая очистка таблиц с отозванными токенами.

В `main_app/celery_app.py` находится конфигурация Celery, используемая основной частью приложения для постановки задач.

В `email_app/celery_email_tasks.py` определена задача отправки электронной почты через SMTP.

В `celery_beat_app/celery_beat_tasks.py` настроены периодические задачи очистки таблиц blacklist.
